The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY follow RFC 2119.
Load `core-main` before your first step when its rules are not in your context.
Load `requirements` before an amendment when its rules are not in your context.

# tracking

## 1. Tracker

- Tracker verbs: read an item (body, comments and labels), list an item's children, in
  order, each with its status, assignee and blockers, create an item, edit an item body,
  link a child to its parent, add a blocked-by edge, claim (assign to the user), comment,
  set the status open, done or dropped; optional: branch name (a read of the tracker's
  branch name for an item, with no side effect), the label verbs: list items (by
  status and label), list labels, set labels (add or remove) and create label, and the
  forge verbs: list a PR's open review threads (unresolved only, each with its id, file,
  line and comments), reply in a thread and resolve a thread. Project context
  `## Tracker` binds each verb. A thread reply MUST count as a comment, and a resolve as
  a write, under the rules below.
- Docs fallback: with no `## Tracker` in project context, milestones, tasks and their
  status live in docs files, not in a tracker.
- Each write MUST be one the approved plan lists. Any other write MUST get user's yes
  first.
- Before a run's first create, main session MUST check that the binding targets project's
  own tracker. It MUST ask user when the target points elsewhere.
- A run MUST put AI marker line `> *This was generated by AI.*` above each text block it
  adds to an existing item body, and at start of each comment and each new item body.
- A run MUST NOT edit body of a parent item (an item above the one the run plans or
  codes), except to write an amendment user approved. It MUST comment on that item
  instead.
- When a bound tracker is unreachable, run MUST stop before tracker step and ask user. It
  MUST NOT use docs fallback.

## 2. Docs and status

- Each planning level MUST keep its doc, its branch and the facts its doc holds as this
  table sets. The table and the bullets above the tracker variant are the docs fallback
  (§1).

| Level | Doc | Branch | Holds |
|---|---|---|---|
| strategic | `<docs>/DESIGN.md`, edited in place | `design-<topic>` | architecture, dated decisions, the milestone list and milestone status |
| milestone | `<docs>/milestones/<name>.md` | `milestone-<name>` | out of scope, the `BR` list, the tasks and their status, risks |
| task | `<docs>/plans/<branch>.md` | the task branch | design, the `TR` list, test scope, risks, overrides, accepted tech debt |

- A `BR` MUST live in the milestone doc. A task with no milestone MUST keep its own `BR`
  list in the plan file.
- With no tracker bound, a task with no milestone MUST take its title slug as its branch.
- Each title slug MUST be ASCII: a non-Latin title transliterated, lower case, words
  joined by `-`.
- Milestone status MUST live only in `<docs>/DESIGN.md`. Task status MUST live only in the
  milestone doc. Status values MUST be open, done and dropped.
- With a tracker bound (§1), this tracker variant MUST replace only the docs-fallback
  rules it names:
  - `<docs>/DESIGN.md` keeps its architecture and decisions and MUST hold no milestone
    list. Each new milestone MUST become a top-level tracker item. Each task of a
    milestone MUST become a child item of the milestone item.
  - A task with no milestone MUST keep its own `BR` list in its own task item body. Plan
    file MUST hold no `BR` text, only `BR` ids.
  - Status MUST live only in the tracker.
  - Task's branch MUST be the tracker's branch name for its item when the binding has
    that verb, else `<item id>-<title slug>`. Plan file path MUST be the branch with each
    `/` replaced by `-`.

## 3. Triage roles

- Roles: states `needs-triage`, `needs-info`, `accepted`; categories `bug`, `enhancement`.
  A triaged inbound item MUST carry exactly one state role and one category role.
- Each role MUST map to its label through its `label <role>: <label>` line in project
  context `## Tracker`, one of the five label lines.
- With the label lines bound, each tracker item a run creates MUST carry one category
  label and no `accepted`: `bug` for a fix, else `enhancement`. A missing role label MUST
  be created first.
- The comment a run adds when it sets `needs-info` MUST take the form
  `## Triage notes`: what is established, and what reporter still needs to give.

## 4. Amendments

- A requirement that changes during work, or needs user's answer, MUST stop work until
  user's yes.
- An added or changed requirement MUST get a new id, unless it is a `TR` edited in place
  (below), and MUST go to user for a yes, with the new text, through the question tool.
  One exception, the `TR` of a defect in built code (below), needs no yes: it repairs
  approved work.
- An added or changed `TR` MUST come as a draft from planner.
- A change user asks for during a code run MUST get its `BR` in the same amendment as its
  `TR`; user's request is the yes for both.
- An amendment MUST go to the doc that owns the fact (§2).
- A `BR` gap found in a task run MUST amend the owning doc, after user's yes: the
  milestone doc on the task branch, or the milestone item with a tracker bound.
- With a tracker bound, an amendment that cites a follow-up item MUST list that item's
  create in its question.
- A task that its milestone doc does not list MUST get its Tasks line as an amendment.
- An amendment that adds a gate-type `BR` (`requirements` §3) MUST also add it to
  each open task of the milestone: to the `<what> : <BR list>` line of each open child
  item body, with the AI marker line above the changed line, or, in the docs fallback, to
  each open task line of the milestone doc. The amendment question MUST list these tracker
  writes.
- A change to the design MUST go back through quizzes, plan and approval. A redesign
  user approves is such a change.
- An architecture gap MUST re-plan at the strategic level, on a `design-<topic>` branch.
- A defect in built code (`requirements` §1) MUST get a new `TR-n` and its test.
- Main session MUST allocate every new id. Subagent MUST NOT allocate one.
- Before next brief or follow-up message, main session MUST have writer write into
  owning doc the new items, each `(replaced by <new id>)` mark, each dated note and the
  line updates below; no reason or history. Writer brief MUST carry the amendment's
  reason and history for writer's commit message; main session MUST also put them into
  tracker comment when one is written.
- A replacing item MUST state its full text. A replaced item MUST keep its id line, never
  renumbered, with the mark `(replaced by <new id>)`; its old text MAY go. Before the
  plan's first commit, an item that user's yes replaces MAY be rewritten in place. Until
  the first brief that names it, a `TR` that user's yes changes MUST be edited in place
  and keep its id.
- Brief or follow-up message of a `TR` that replaces another MUST tell the coder to
  re-point each `req:` marker of the old id to the new id.
- A wrong `tests:` case of a `TR` whose behavior stays MUST get a dated note below the
  `TR` list that names the `TR` and gives the corrected case. A changed behavior takes a
  new id (above).
- When a code run starts on a plan whose commit is behind `<base>`, main session MUST
  first have an agent check each `TR` against `<base>`. Each `TR` that `<base>` already
  meets MUST get a dated note below the `TR` list. Done when each `TR` is checked.
- When an amendment replaces or removes a term, id, design choice or figure (a profile,
  a file, a class, a bound), main session MUST have the owning doc, plan file and project
  context grepped for it before it asks user: by a short read when that settles it, else
  by a researcher that returns the id of each line naming it. Each requirement line that
  names it MUST join that amendment's question, with its new id, and get its
  `(replaced by <new id>)` mark at the amendment commit. A `needs:` line that names a
  replaced id MUST be updated in place at that commit, with no new id.
- Before the amendment commit, main session MUST have an agent list each line that is not
  a requirement (Goal, Design, Risks, Test scope) and that the amendment makes false. The
  amendment commit MUST update each such line. An amendment that changes a tested
  behavior or a data shape MUST add each case it breaks to Test scope in the same
  commit. A line with an `Unverified:` part that a `TR` proves MUST be deleted.

## 5. Business quiz

- Business quiz topics: goal, who is affected, done criteria, users, features, business
  rules, out of scope, constraints.
- A strategic run that adds a milestone for new user-facing work MUST also take the topic
  pre-mortem: it MUST propose the assumption most likely to make the work useless, the
  smallest evidence that tests it, and what to delay until that evidence is in. A
  milestone that gathers that evidence SHOULD come first in the milestone list. Done when
  user accepted or changed the three items.
